# V15 安全編碼和架構

## 控制目標

許多 ASVS 要求要麼與身分驗證、授權等特定安全領域相關，要麼與日誌、檔案處理等特定類型的應用功能相關。

本章給出設計和開發應用時普遍適用的安全要求，既涉及清晰的架構和程式碼品質，也涉及保障應用程式安全所必需的架構設計與編碼實踐。

## V15.1 安全編碼和架構文件

要建立安全且具備防禦能力的架構，許多要求都依賴清晰的文件，以記錄特定安全控制和應用所用元件的實作決策。

本節概述文件要求，包括識別被視為包含「危險功能」或屬於「風險元件」的元件。

「危險功能」可能存在於內部元件或第三方元件中，包括反序列化不可信資料、解析原始檔案或二進位資料、動態執行程式碼，以及直接操作記憶體。這類功能一旦出現弱點，往往會導致應用被攻破，甚至危及底層基礎設施。

「風險元件」是指開發流程或功能缺少安全控制，或者安全控制實作較差的第三方函式庫（即非內部開發函式庫）。例如維護不佳、不再受支援、已到生命週期末期或曾出現重大弱點的元件。

本節還強調為修復第三方元件弱點定義合適時限的重要性。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **15.1.1** | 驗證應用文件根據風險規定了修復第三方元件已知弱點的時限，以及常規更新相依函式庫的時限，從而盡量降低元件風險。 | 1 |
| **15.1.2** | 驗證應用維護了所有在用第三方函式庫的清單，例如軟體物料清單（SBOM），並確認每個元件都來自預先指定、可信且持續維護的倉庫。 | 2 |
| **15.1.3** | 驗證應用文件列出了執行時間較長，或會大量佔用計算、記憶體、連線等系統資源的功能，並說明如何防止這些功能被過度使用而導致應用不可用，以及如何避免回應生成時間超過呼叫方的逾時限制。可採用非同步處理、工作佇列，並限制每個使用者及整個應用同時執行的任務數量等措施。 | 2 |
| **15.1.4** | 驗證應用文件標出被視為「風險元件」的第三方函式庫。 | 3 |
| **15.1.5** | 驗證應用文件標出應用中正在使用「危險功能」的部分。 | 3 |

## V15.2 安全架構和依賴

本節說明如何通過依賴管理處理高風險、過時或不安全的依賴和元件。

本節還要求採用沙箱、封裝、容器化和網路隔離等架構措施，限制「危險功能」或「風險元件」遭到利用後的影響，並防止大量佔用系統資源的功能被濫用而導致應用不可用。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **15.2.1** | 驗證應用中的所有元件都仍處於文件規定的更新和弱點修復期限內。 | 1 |
| **15.2.2** | 驗證應用按照書面的安全決策和策略實施了防護，避免執行時間較長或大量佔用系統資源的功能影響應用可用性。 | 2 |
| **15.2.3** | 驗證正式環境只包含應用執行所必需的功能，不暴露測試程式碼、示例片段和開發功能等額外功能。 | 2 |
| **15.2.4** | 驗證第三方元件及其所有傳遞依賴均來自預期的倉庫，無論倉庫由內部持有還是來自外部，並且不存在依賴混淆攻擊的風險。 | 3 |
| **15.2.5** | 驗證應用對文件中標記為包含「危險功能」或使用「風險元件」第三方函式庫的部分實施額外保護。保護措施可以包括沙箱、封裝、容器化或網路級隔離等技術，以延緩並阻止已攻破應用某一部分的攻擊者橫向移動到應用其他位置。 | 3 |

## V15.3 防禦式編碼

本節討論由程式語言中的不安全寫法引發的弱點，例如類型轉換混淆和原型污染。有些弱點只出現在特定語言中，也可能需要採用特定語言的修復方式；另一些則取決於語言或框架如何處理 HTTP 參數等功能。本節還考慮未通過密碼學手段驗證應用更新所帶來的風險。

本節還討論應用通過外部 API 接收或傳回資料物件時可能產生的風險。接收資料時，應用必須防止使用者通過輸入修改本不允許其修改的欄位（即大量指派）；傳回資料時，API 必須只傳回必要的欄位。如果使用者能否存取某個欄位取決於其權限，還必須遵循「授權」章節中有關欄位級存取控制的要求。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **15.3.1** | 驗證應用只傳回資料物件中所需的欄位子集。例如，不應傳回整個資料物件，因為其中某些欄位不應供使用者存取。 | 1 |
| **15.3.2** | 驗證應用後端呼叫外部 URL 時，組態為不跟隨重新導向，除非跟隨重新導向是預期功能。 | 2 |
| **15.3.3** | 驗證應用針對每個控制器和操作限制允許的欄位，以防範大量指派攻擊。例如，使用者不得通過請求插入或更新該功能原本不允許處理的欄位。 | 2 |
| **15.3.4** | 驗證所有代理和中介軟體都通過最終使用者無法篡改的可信欄位傳遞使用者原始 IP 位址，應用和 Web 伺服器則使用這個可信值進行日誌記錄、速率限制等安全決策。同時應認識到，動態 IP、VPN 和企業防火牆等因素仍會降低原始 IP 位址的可靠性。 | 2 |
| **15.3.5** | 驗證應用明確確保變數類型正確，並執行嚴格的相等和比較運算，以避免應用程式碼對變數類型作出假設而導致類型轉換混淆或類型混淆弱點。 | 2 |
| **15.3.6** | 驗證 JavaScript 程式碼採用能夠防範原型污染的寫法，例如使用 `Set()` 或 `Map()`，而不是使用物件常值。 | 2 |
| **15.3.7** | 驗證應用具備防禦 HTTP 參數污染攻擊的措施，尤其是在應用框架不區分請求參數來源（查詢字串、正文參數、Cookie 或標頭欄位）時。 | 2 |

## V15.4 安全併發

併發問題，例如競態條件、檢查時到使用時（TOCTOU）弱點、死鎖、活鎖、執行緒飢餓和不當同步，可能導致不可預測行為和安全風險。本節包含幫助緩解這些風險的多種技術和策略。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **15.4.1** | 驗證多執行緒程式碼通過執行緒安全類型以及鎖、號誌等同步機制來存取共享物件，例如快取、檔案或多執行緒共用的記憶體物件，以避免競態條件和資料損壞。 | 3 |
| **15.4.2** | 驗證對資源狀態（例如是否存在或權限）的檢查及依賴檢查結果的操作，作為單個原子操作執行，以防範檢查時到使用時（TOCTOU）競態條件。例如，開啟檔案前檢查檔案是否存在，或授予使用者存取權限前驗證其存取權限。 | 3 |
| **15.4.3** | 驗證應用採用一致的加鎖規則，避免執行緒因相互等待或無限重試而卡死。加鎖邏輯保留在負責管理相應資源的程式碼中，防止外部類別或其他程式碼無意或惡意地修改鎖。 | 3 |
| **15.4.4** | 驗證資源分配策略保證各執行緒能夠公平獲得資源，防止執行緒飢餓。例如，使用執行緒池並確保低優先級執行緒也能在合理時間內繼續執行。 | 3 |
