# V9 自包含權杖

## 控制目標

2012 年發佈的 OAuth 2.0 原始規範 RFC 6749 提到了自包含權杖的概念。所謂自包含權杖，是指權杖本身攜帶資料或宣告，接收服務可以直接依據這些內容作出安全決策。與之不同的是，有些權杖只包含一個識別碼，接收服務必須使用該識別碼在本地查詢實際資料。常見的自包含權杖包括 JSON Web Token（JWT）和 SAML 斷言。

如今，自包含權杖已經廣泛使用，甚至用於 OAuth 和 OIDC 之外的場景。這一機制的安全性依賴於驗證權杖完整性，並確認權杖在特定情境中有效的能力。這一過程存在許多陷阱，本章詳細說明了應用應採取的防範機制。

## V9.1 權杖來源和完整性

本節要求應用確認權杖由可信方簽發，並驗證權杖內容沒有遭到篡改。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **9.1.1** | 驗證應用在接受自包含權杖中的任何內容之前，會使用數位簽章或訊息鑑別碼（MAC）驗證權杖完整性，確認其內容沒有遭到篡改。 | 1 |
| **9.1.2** | 驗證建立和檢核自包含權杖時，只允許使用當前場景預先批准的演算法。演算法允許清單不得包含 `None`，並且最好只允許使用對稱演算法或非對稱演算法中的一類。如果必須同時支援這兩類演算法，則必須採取額外措施防止金鑰混淆。 | 1 |
| **9.1.3** | 驗證用於檢核自包含權杖的金鑰資料，來自預先為相應權杖簽發方組態的可信來源，以防止攻擊者指定不可信的來源和金鑰。對於 JWT 和其他 JWS 結構，必須對照可信來源允許清單檢查 `jku`、`x5u`、`jwk` 等標頭欄位。 | 1 |

## V9.2 權杖內容

服務根據自包含權杖中的內容作出安全決策前，必須確認該權杖仍在有效期內、允許由當前服務使用，並且權杖類型符合當前用途。這樣可以防止一個服務接受原本簽發給另一個服務的權杖，也可以防止混用同一簽發方簽發的不同類型權杖。

OAuth 和 OIDC 的相關具體要求見專門章節。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **9.2.1** | 驗證權杖中規定了有效時間範圍時，接收方只在檢核時間位於該範圍內時，才接受權杖及其中的內容。對於 JWT，必須檢查 `nbf` 和 `exp` 宣告。 | 1 |
| **9.2.2** | 驗證服務在接受權杖內容之前，會確認權杖類型正確，並且符合當前使用目的。例如，只有存取權杖可以用於授權決策，只有 ID Token 可以用於證明使用者已經完成身分驗證。 | 2 |
| **9.2.3** | 驗證服務在接受權杖前，會確認該權杖的預期接收方（受眾）包含本服務。對於 JWT，可以通過對照服務中定義的允許清單驗證 `aud` 宣告來實作。 | 2 |
| **9.2.4** | 驗證簽發方使用同一私密金鑰為不同受眾簽發權杖時，簽發的權杖包含能夠唯一識別預期受眾的受眾限制，以防止權杖被非預期受眾重複使用。受眾識別碼採用動態分配方式時，簽發方必須驗證這些受眾，確保不會導致受眾冒充。 | 2 |
