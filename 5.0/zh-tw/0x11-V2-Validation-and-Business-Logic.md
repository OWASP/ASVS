# V2 驗證和業務邏輯

## 控制目標

本章要求接受驗證的應用達到以下總體目標：

* 應用接收的輸入符合業務或功能預期。
* 業務邏輯流程按預期順序逐步處理，不能被繞過。
* 業務邏輯包含限制和控制，用於檢測並防止自動化攻擊，例如連續進行小額轉賬，或一次添加一個好友直到添加一百萬個。
* 高價值業務邏輯流程已考慮濫用場景和惡意行為者，並具備防範欺騙、篡改、資訊洩露和權限提升攻擊的保護措施。

## V2.1 驗證和業務邏輯文件

驗證規則和業務邏輯文件應清楚說明業務限制、輸入驗證規則，以及多個相關資料項之間應滿足的邏輯關係，讓開發和測試人員明確應用必須實作哪些約束。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **2.1.1** | 驗證應用文件明確規定了輸入驗證規則，包括如何按照預期結構檢查資料是否有效。規則既可以針對信用卡號、電子郵件位址、電話號碼等常見格式，也可以針對應用內部的資料格式。 | 1 |
| **2.1.2** | 驗證應用文件明確規定了如何檢查多個相關資料項在邏輯和情境上是否一致，例如市郊地區與郵政編碼是否匹配。 | 2 |
| **2.1.3** | 驗證應用文件明確規定了業務邏輯限制和驗證要求，包括針對單個使用者的限制，以及適用於整個應用的全局限制。 | 2 |

## V2.2 輸入驗證

有效的輸入驗證控制應根據應用預期接收的資料類型，落實相應的業務或功能要求。這可以保證良好的資料品質，並縮小攻擊面。但在其他元件中使用這些資料或將其用於輸出時，仍需進行正確的編碼、參數化或淨化，輸入驗證不能消除或取代這些需求。

在此語境下，「輸入」可能來自多種來源，包括 HTML 表單欄位、REST 請求、URL 參數、HTTP 頭欄位、Cookie、磁碟文件、資料庫和外部 API。

例如，業務規則可能要求某個輸入必須是小於 100 的數字。功能規則也可能為控制循環次數的參數設定上限，防止數值過大造成過量計算，進而引發拒絕服務。

本標準沒有明確強制要求採用模式驗證。不過，對於使用 JSON 或 XML 的 HTTP API 或其他介面，模式驗證可能是實作完整驗證覆蓋的最有效機制。

請注意以下關於模式驗證的要點：

* JSON Schema 驗證規範的「已發佈版本」被認為可用於生產環境，但嚴格來說並不算「穩定」。使用 JSON Schema 驗證時，應確保與下列要求中的指導不存在缺口。
* 正在使用的任何 JSON Schema 驗證庫，也應在標準正式確定後持續監控，並在必要時更新。
* 不應使用 DTD 驗證，並且應停用框架的 DTD 求值，以避免 DTD 相關 XXE 攻擊問題。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **2.2.1** | 驗證對輸入進行驗證，以落實該輸入對應的業務或功能要求。應根據值、模式和範圍的允許列表進行正向驗證，或按照預先定義的規則，將輸入與預期結構及邏輯限制進行比較。L1 可以重點驗證用於作出特定業務或安全決策的輸入；L2 及以上應對所有輸入進行驗證。 | 1 |
| **2.2.2** | 驗證應用在可信服務層強制執行輸入驗證。用戶端驗證有助於改善使用體驗，應予鼓勵，但不得將其作為安全控制加以依賴。 | 1 |
| **2.2.3** | 驗證應用按照預先定義的規則，檢查多個相關資料項組合在一起後是否合理。 | 2 |

## V2.3 業務邏輯安全

本節說明如何確保應用按照預期執產業務流程，並防範攻擊者利用流程設計或業務邏輯缺陷。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **2.3.1** | 驗證應用按照預期的連續步驟順序為同一使用者處理業務邏輯流程，不允許跳過任何步驟。 | 1 |
| **2.3.2** | 驗證應用按照文件規定落實了各項業務邏輯限制，防止攻擊者利用業務邏輯缺陷。 | 2 |
| **2.3.3** | 驗證業務邏輯層使用事務來執行相關操作，使整組操作要麼全部成功，要麼回復到操作前的正確狀態。 | 2 |
| **2.3.4** | 驗證業務邏輯層採用了適當的鎖定機制，防止攻擊者通過操縱應用流程重複預訂數量有限的資源，例如劇院座位或配送時段。 | 2 |
| **2.3.5** | 驗證高價值業務流程必須經過多人審批，以防止未經授權或誤操作。此類流程可能包括但不限於大額資金轉賬、合同審批、存取涉密資訊，或在製造過程中繞過安全保護。 | 3 |

## V2.4 反自動化

本節包含反自動化控制，要求互動方式符合人工操作特徵，並防止過量的自動化請求。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **2.4.1** | 驗證應用採用了反自動化控制，防止應用功能被過量呼叫。這類濫用可能造成資料外洩、產生大量垃圾資料、耗盡配額、規避速率限制、拒絕服務，或大量消耗高成本資源。 | 2 |
| **2.4.2** | 驗證業務流程對操作節奏作出限制，使其符合真實使用者的操作速度，防止業務操作被異常快速地連續提交。 | 3 |
