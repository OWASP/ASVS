# V6 身分驗證

## 控制目標

身分驗證是確認個人或裝置真實身分的過程。身分驗證機制需要確認主體聲稱的身分，防止他人冒充，並防止密碼被復原或截獲。

[NIST SP 800-63](https://pages.nist.gov/800-63-3/) 是一套以研究證據為基礎的現代數位身分標準，對世界各地的組織都有參考價值，尤其適用於美國機構及其合作組織。

本章許多要求源自該標準的第二部分，即 NIST SP 800-63B《數位身分指南——身分驗證和生命週期管理》。不過，本章只重點討論常見威脅和經常遭到利用的身分驗證弱點，並不覆蓋該標準的全部內容。如需完整遵循 NIST SP 800-63，請直接查閱該標準。

此外，NIST SP 800-63 的術語有時不同；為提高清晰度，本章通常使用更容易理解的常用術語。

較為先進的應用通常能夠根據各種風險因素調整所需的身分驗證步驟。該特性在「授權」章節中介紹，因為這些機制也需要納入授權決策。

## V6.1 身分驗證文件

本節規定應用需要維護哪些身分驗證文件。清楚的文件是正確組態和評估身分驗證控制的前提。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **6.1.1** | 驗證應用文件說明了如何利用速率限制、反自動化和自適應回應等控制，防範撞庫攻擊（credential stuffing）和密碼暴力破解。文件必須寫明這些控制的組態方式，以及如何避免攻擊者惡意觸發帳號鎖定。 | 1 |
| **6.1.2** | 驗證文件記錄了與應用具體情境相關的停用詞表，防止這些詞被用於密碼。詞表可以包括組織名稱、產品名稱、系統識別碼、專案代號、部門或角色名稱，以及這些名稱的常見變體。 | 2 |
| **6.1.3** | 驗證應用存在多條身分驗證路徑時，文件列出了所有路徑，並規定了各條路徑必須一致採用的安全控制和身分驗證強度。 | 2 |

## V6.2 密碼安全

NIST SP 800-63 把使用者需要記住的身分驗證資訊統稱為「記憶秘密」，其中包括密碼、通關片語、PIN、解鎖圖案，以及選出正確的小貓或其他圖像元素等方式。這些資訊屬於「使用者知道的內容」，經常用於單因素身分驗證。

因此，本節包含確保密碼被安全建立和處理的要求。大多數要求屬於 L1，因為它們在該等級最重要。從 L2 開始，需要多因素身分驗證機制，而密碼可能只是其中一個因素。

本節要求主要與 [NIST 指南](https://pages.nist.gov/800-63-3/sp800-63b.html)的 [&sect; 5.1.1.2](https://pages.nist.gov/800-63-3/sp800-63b.html#memsecretver) 相關。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **6.2.1** | 驗證使用者設定的密碼至少包含 8 個字元；強烈建議把最短長度提高到 15 個字元。 | 1 |
| **6.2.2** | 驗證使用者可以修改自己的密碼。 | 1 |
| **6.2.3** | 驗證密碼修改功能要求使用者提供當前密碼和新密碼。 | 1 |
| **6.2.4** | 驗證使用者註冊帳號或修改密碼時，應用會把新密碼與常見密碼清單進行比對。清單至少應包含符合應用密碼政策（例如最短長度）的最常見的 3000 個密碼。 | 1 |
| **6.2.5** | 驗證應用允許使用者自由組合密碼中的字元，不以複雜度規則限制字元類型。不得強制密碼必須包含一定數量的大寫字母、小寫字母、數字或特殊字元。 | 1 |
| **6.2.6** | 驗證密碼輸入框使用 `type=password` 遮蔽輸入內容。應用可以允許使用者臨時顯示完整密碼，也可以只短暫顯示最後輸入的字元。 | 1 |
| **6.2.7** | 驗證密碼輸入框允許貼上，並支援瀏覽器的密碼輔助功能和第三方密碼管理器。 | 1 |
| **6.2.8** | 驗證應用完全按照使用者提交的原始內容檢核密碼，不得截斷密碼，也不得改變字母大小寫或進行其他轉換。 | 1 |
| **6.2.9** | 驗證應用支援長度至少為 64 個字元的密碼。 | 2 |
| **6.2.10** | 驗證使用者密碼在確認已經洩露或使用者主動更換之前始終有效。應用不得要求定期更換身分驗證資訊。 | 2 |
| **6.2.11** | 驗證應用使用文件中規定的與具體情境相關的停用詞表，阻止使用者設定容易猜中的密碼。 | 2 |
| **6.2.12** | 驗證使用者註冊帳號或修改密碼時，應用會把新密碼與已知洩露密碼庫進行比對。 | 2 |

## V6.3 通用身分驗證安全

本節規定身分驗證機制普遍需要滿足的安全要求，並區分不同驗證等級。L2 應用必須強制使用多因素身分驗證（MFA）。L3 應用必須採用基於硬體的身分驗證，且身分驗證必須在經過證明的可信執行環境（TEE）中執行。例如，可以使用與裝置綁定的通行金鑰、達到 eIDAS 高保證等級（LoA High）的驗證器、達到 NIST 驗證器保證等級 3（AAL3）的驗證器，或同等強度的機制。

這些 MFA 要求較為嚴格，但提高身分驗證門檻對保護使用者十分重要。如果嘗試放寬這些要求，應制定明確方案，說明如何緩解身分驗證風險，並考慮 NIST 指南及相關研究。

請注意，在發佈時，NIST SP 800-63 將電子郵件視為[不可接受](https://pages.nist.gov/800-63-FAQ/#q-b11)的身分驗證機制（[歸檔副本](https://web.archive.org/web/20250330115328/https://pages.nist.gov/800-63-FAQ/#q-b11)）。

本節要求涉及 [NIST 指南](https://pages.nist.gov/800-63-3/sp800-63b.html)中的多個章節，包括：[&sect; 4.2.1](https://pages.nist.gov/800-63-3/sp800-63b.html#421-permitted-authenticator-types)、[&sect; 4.3.1](https://pages.nist.gov/800-63-3/sp800-63b.html#431-permitted-authenticator-types)、[&sect; 5.2.2](https://pages.nist.gov/800-63-3/sp800-63b.html#522-rate-limiting-throttling) 和 [&sect; 6.1.2](https://pages.nist.gov/800-63-3/sp800-63b.html#-612-post-enrollment-binding)。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **6.3.1** | 驗證應用按照安全文件落實了防範撞庫攻擊（credential stuffing）和密碼暴力破解的控制措施。 | 1 |
| **6.3.2** | 驗證應用不存在仍可使用的預設帳號，例如 `root`、`admin` 或 `sa`；如有此類帳號，必須將其停用。 | 1 |
| **6.3.3** | 驗證使用者必須通過多因素身分驗證，或者組合使用多個單因素身分驗證機制，才能存取應用。對於 L3，至少一個因素必須採用基於硬體的身分驗證機制，能夠抵抗網路釣魚造成的身分驗證資訊洩露和身分冒充；該機制還必須要求使用者主動操作（例如按下 FIDO 硬體金鑰或手機上的按鈕），以確認使用者確實有意登入。若要放寬其中任何一項要求，必須完整記錄理由，並配套一組充分的補償控制。 | 2 |
| **6.3.4** | 驗證應用包含多條身分驗證路徑時，所有路徑都已記錄，並且各條路徑一致地執行安全控制和身分驗證強度要求。 | 2 |
| **6.3.5** | 驗證應用會把可疑的身分驗證嘗試通知使用者，無論嘗試成功還是失敗。可疑情形可能包括從異常地點或用戶端發起身分驗證、多因素身分驗證中只有部分因素通過、帳號長期未使用後出現身分驗證嘗試，以及連續多次失敗後突然身分驗證成功。 | 3 |
| **6.3.6** | 驗證應用不把電子郵件用作單因素身分驗證，也不把它用作多因素身分驗證中的一個因素。 | 3 |
| **6.3.7** | 驗證身分驗證資訊發生變更後，應用會通知使用者，例如重設身分驗證資訊，或者修改使用者名稱、電子郵件位址。 | 3 |
| **6.3.8** | 驗證攻擊者無法根據失敗的身分驗證結果判斷某個使用者是否存在，包括無法利用錯誤訊息、HTTP 狀態碼或回應時間差異進行推斷。帳號註冊和忘記密碼功能也必須提供同等保護。 | 3 |

## V6.4 身分驗證因素生命週期和復原

身分驗證因素可以包括密碼、軟權杖、硬體權杖和生物辨識裝置。安全處理這些機制的生命週期對應用程式安全至關重要，本節包含相關要求。

本節要求主要與 [NIST 指南](https://pages.nist.gov/800-63-3/sp800-63b.html)的 [&sect; 5.1.1.2](https://pages.nist.gov/800-63-3/sp800-63b.html#memsecretver) 或 [&sect; 6.1.2.3](https://pages.nist.gov/800-63-3/sp800-63b.html#replacement) 相關。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **6.4.1** | 驗證系統生成的初始密碼或啟用碼採用安全的隨機方式生成，符合現行密碼政策，並在較短時間後或首次使用後失效。不得允許這些初始秘密成為長期密碼。 | 1 |
| **6.4.2** | 驗證應用沒有使用密碼提示，也沒有使用所謂「秘密問題」等基於知識的身分驗證方式。 | 1 |
| **6.4.3** | 驗證應用提供了安全的忘記密碼重設流程，並且該流程不會繞過已經啟用的多因素身分驗證。 | 2 |
| **6.4.4** | 驗證使用者丟失多因素身分驗證中的某個因素時，應用會採用與註冊該因素時同等強度的身分核驗流程。 | 2 |
| **6.4.5** | 驗證應用會在身分驗證機制到期前留出足夠時間，向使用者傳送續期說明，使使用者能夠在原機制失效前完成續期；必要時還應自動提醒使用者。 | 3 |
| **6.4.6** | 驗證管理員可以為使用者發起密碼重設，但不能替使用者指定或修改密碼，從而避免管理員知曉使用者密碼。 | 3 |

## V6.5 通用多因素身分驗證要求

本節提供適用於多種不同多因素身分驗證方法的一般指導。

這些機制包括：

* 查表型秘密
* 基於時間的一次性密碼（TOTP）
* 帶外機制

查表型秘密（look-up secret）是預先產生的一組秘密碼，例如交易授權碼（TAN）、社交媒體復原碼，或由隨機值組成的代碼表。這些秘密碼通常難以記憶，需要保存在某種介質中，因此屬於「使用者擁有的內容」。

基於時間的一次性密碼（TOTP）由硬體權杖或軟體權杖生成，顯示會隨時間變化的偽隨機一次性密碼，因此也屬於「使用者擁有的內容」。多因素 TOTP 與單因素 TOTP 類似，但生成最終的一次性密碼（OTP）前，還要求輸入有效 PIN、透過生物辨識解鎖、插入 USB 裝置或完成 NFC 配對，或輸入某個附加值（例如使用交易簽章計算器時）。

帶外機制的細節將在下一節提供。

這些章節中的要求主要與 [NIST 指南](https://pages.nist.gov/800-63-3/sp800-63b.html)的 [&sect; 5.1.2](https://pages.nist.gov/800-63-3/sp800-63b.html#-512-look-up-secrets)、[&sect; 5.1.3](https://pages.nist.gov/800-63-3/sp800-63b.html#-513-out-of-band-devices)、[&sect; 5.1.4.2](https://pages.nist.gov/800-63-3/sp800-63b.html#5142-single-factor-otp-verifiers)、[&sect; 5.1.5.2](https://pages.nist.gov/800-63-3/sp800-63b.html#5152-multi-factor-otp-verifiers)、[&sect; 5.2.1](https://pages.nist.gov/800-63-3/sp800-63b.html#521-physical-authenticators) 和 [&sect; 5.2.3](https://pages.nist.gov/800-63-3/sp800-63b.html#523-use-of-biometrics) 相關。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **6.5.1** | 驗證每個查表型秘密、帶外身分驗證請求或驗證碼，以及基於時間的一次性密碼（TOTP），最多只能成功使用一次。 | 2 |
| **6.5.2** | 驗證儲存在應用後端的查表型秘密如果少於 112 位元熵（約相當於 19 個隨機英數字元或 34 個隨機數字），會使用獲批准的密碼儲存雜湊演算法和 32 位元隨機鹽值進行雜湊。秘密達到或超過 112 位元熵時，可以改用普通的密碼學雜湊函數。 | 2 |
| **6.5.3** | 驗證查表型秘密、帶外驗證碼和 TOTP 種子都由密碼學安全偽亂數產生器（CSPRNG）生成，避免生成可預測的值。 | 2 |
| **6.5.4** | 驗證查表型秘密和帶外驗證碼至少包含 20 位元熵，通常 4 個隨機英數字元或 6 個隨機數字即可滿足要求。 | 2 |
| **6.5.5** | 驗證應用為帶外身分驗證請求、驗證碼或權杖以及 TOTP 設定了明確的有效期。帶外身分驗證請求的有效期最長為 10 分鐘，TOTP 的有效期最長為 30 秒。 | 2 |
| **6.5.6** | 驗證包括實體裝置在內的任何身分驗證因素，在被盜或丟失後都可以撤銷。 | 3 |
| **6.5.7** | 驗證生物辨識只能作為輔助因素，必須與「使用者擁有的內容」或「使用者知道的內容」配合使用。 | 3 |
| **6.5.8** | 驗證 TOTP 使用可信服務提供的時間源進行檢核，不採用不可信來源或用戶端提供的時間。 | 3 |

## V6.6 帶外身分驗證機制

帶外身分驗證通常由身分驗證伺服器通過另一條安全通道與使用者裝置通訊，例如向手機傳送推送通知。由於身分驗證依賴使用者持有該裝置，因此屬於「使用者擁有的內容」。

不得使用電子郵件、VoIP 等不安全的帶外身分驗證方式。NIST 目前把通過 PSTN 或 SMS 進行的身分驗證列為[「受限」身分驗證機制](https://pages.nist.gov/800-63-FAQ/#q-b01)，應用應逐步停用這些方式，改用 TOTP、密碼學身分驗證或類似機制。NIST SP 800-63B [&sect; 5.1.3.3](https://pages.nist.gov/800-63-3/sp800-63b.html#-5133-authentication-using-the-public-switched-telephone-network) 指出，如果確實必須保留電話或 SMS 帶外身分驗證，就應處理更換裝置、更換 SIM 卡、號碼攜轉和其他異常行為帶來的風險。本 ASVS 小節雖然沒有把這些措施列為強制要求，但敏感的 L2 應用和所有 L3 應用如果沒有採取相應措施，應視為存在重大風險。

請注意，NIST 最近還提供了[不鼓勵使用推送通知](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/#fig-3)的指導。雖然本 ASVS 小節沒有這樣規定，但瞭解「推送轟炸」風險很重要。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **6.6.1** | 驗證應用只有同時滿足以下條件時，才允許通過公共交換電話網路（PSTN）的語音電話或 SMS 傳送一次性密碼（OTP）：電話號碼已經預先驗證；同時提供 TOTP 等更強的替代方式；並且已經向使用者說明其中的安全風險。L3 應用不得提供電話或 SMS 身分驗證。 | 2 |
| **6.6.2** | 驗證每個帶外身分驗證請求、驗證碼或權杖都與產生它的那一次身分驗證請求綁定，不能挪用於之前或之後的其他請求。 | 2 |
| **6.6.3** | 驗證基於驗證碼的帶外身分驗證採用速率限制來防範暴力破解。也可以考慮使用至少包含 64 位元熵的驗證碼。 | 2 |
| **6.6.4** | 驗證使用推送通知進行多因素身分驗證時，應用通過速率限制防範「推送轟炸」。數字匹配也可以降低這類風險。 | 3 |

## V6.7 密碼學身分驗證機制

密碼學身分驗證機制包括智慧卡和 FIDO 安全金鑰等。使用者需要把密碼學裝置連接或配對到電腦，才能完成身分驗證。身分驗證伺服器向裝置或軟體傳送一個挑戰值（nonce），裝置或軟體再使用安全儲存的密碼學金鑰計算回應。本節說明這類機制的實作要求；演算法選擇方面的要求見「密碼學」章節。

如果密碼學身分驗證使用共享金鑰或秘密金鑰，這些金鑰應使用與其他系統秘密相同的機制進行儲存，具體見「組態」章節中的「秘密管理」小節。

本節要求主要與 [NIST 指南](https://pages.nist.gov/800-63-3/sp800-63b.html)的 [&sect; 5.1.7.2](https://pages.nist.gov/800-63-3/sp800-63b.html#sfcdv) 相關。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **6.7.1** | 驗證用於核驗密碼學身分驗證斷言的憑證採用防篡改方式儲存。 | 3 |
| **6.7.2** | 驗證挑戰值（nonce）至少為 64 位元，並且在統計意義上不會重複，或者保證在密碼學裝置的整個生命週期內不重複。 | 3 |

## V6.8 使用身分提供方進行身分驗證

身分提供方（IdP）為使用者提供聯合身分。使用者通常會在多個 IdP 中擁有多個身分，例如使用 Azure AD、Okta、Ping Identity 或 Google 的企業身分，或使用 Facebook、Twitter、Google、WeChat 等個人身分。這些只是常見選擇，並不代表對這些公司或服務的認可，而是提醒開發人員考慮一個現實：許多使用者已經擁有多個既有身分。組織應根據 IdP 身分核驗強度的風險評估，考慮是否與現有使用者身分整合。例如，政府組織不太可能接受社交媒體身分作為敏感系統的登入方式，因為這類身分很容易偽造或僅供一次性使用；而行動遊戲公司則很可能需要與主要社交媒體平台整合，以擴大活躍玩家群體。

安全使用外部身分提供方需要謹慎組態和驗證，以防止身分冒充或偽造斷言。本節提供處理這些風險的要求。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **6.8.1** | 驗證應用支援多個身分提供方（IdP）時，使用者身分不能通過另一個受支援的 IdP 被冒充，例如通過使用相同的使用者識別碼進行冒充。通常，應用應把 IdP 識別作為命名空間，並將其與使用者在該 IdP 中的識別組合起來，用於註冊和識別使用者。 | 2 |
| **6.8.2** | 驗證始終檢查身分驗證斷言（例如 JWT 或 SAML 斷言）是否帶有數位簽章，以及簽章是否完整有效，並拒絕任何未簽章或簽章無效的斷言。 | 2 |
| **6.8.3** | 驗證每條 SAML 斷言在有效期內只處理一次，不能重複使用，從而防範重放攻擊。 | 2 |
| **6.8.4** | 驗證應用使用外部身分提供方（IdP）時，如果某項功能要求特定的身分驗證強度、身分驗證方式或身分驗證時效性，就會根據 IdP 傳回的資訊確認要求是否滿足。例如，使用 OIDC 時，可以檢查 ID Token 中的 `acr`、`amr` 和 `auth_time` 宣告（如有）。如果 IdP 不提供這些資訊，應用必須有文件化的回退方案，並在方案中假定使用了最低強度的身分驗證機制，例如使用使用者名稱和密碼的單因素身分驗證。 | 2 |
