# 什麼是 ASVS？

應用程式安全驗證標準（Application Security Verification Standard，ASVS）為 Web 應用和服務定義了安全要求。對於希望設計、開發、維護安全應用，或評估應用程式安全性的人來說，它都是一份有價值的資源。

本章概述使用 ASVS 時需要理解的關鍵內容，包括它的範圍、基於優先級的分級結構，以及該標準的主要使用場景。

## ASVS 的範圍

ASVS 的範圍可以從名稱中的四個詞來理解：應用、安全、驗證和標準。這四個方面共同決定了哪些要求應納入本標準。ASVS 的總體目標是明確應用必須落實的安全原則。文件要求也在其範圍之內，因為相關文件是正確實作安全要求的基礎。

對攻擊者來說，並不存在所謂的範圍邊界。因此，在評估 ASVS 要求時，也應結合應用生命週期其他方面的指南，包括 CI/CD 流程、託管環境和維運活動。

### 應用

ASVS 將「應用」定義為正在開發的軟體產品，安全控制必須整合到其中。ASVS 不規定開發生命週期活動，也不規定如何通過 CI/CD 管線建置應用；它規定的是產品本身必須達到的安全結果。

Web 應用防火牆（WAF）、負載平衡器和代理等元件會轉發、修改或檢查 HTTP 流量。由於某些安全控制需要依靠這些元件實作，因此在相關場景下，可將它們視為應用的一部分。例如，驗證回應快取、速率限制，以及按來源或目的位址限制出入站連線等要求時，都應將這些元件納入評估範圍。

相反，ASVS 通常不包含那些與應用沒有直接關係，或組態不屬於應用職責範圍的要求。例如，DNS 問題通常由獨立團隊或職能負責。

同樣，應用負責自身處理輸入和生成輸出的方式，而與應用或其資料互動的外部流程不屬於 ASVS 的範圍。例如，應用及其資料的備份通常由外部流程負責，不受應用或其開發人員直接控制。

### 安全

每條要求都必須對安全有明確且可驗證的作用。不滿足該要求會削弱應用的安全性；落實該要求，則必須能夠降低某項安全風險發生的可能性或減輕其影響。

其他考慮因素，例如功能特性、程式碼風格或策略要求，都不屬於本標準範圍。

### 驗證

要求必須可以驗證，而且驗證結果必須能得出「失敗」或「通過」的結論。

### 標準

ASVS 是一套可用於判斷應用是否符合標準的安全要求。因此，要求只規定必須達到的安全目標。實作指南、測試方法等相關內容，可以在 ASVS 的基礎上另行編寫，或通過映射與 ASVS 關聯。

具體來說，OWASP 有許多專案，ASVS 有意避免與其他專案的內容重疊。例如，開發人員可能會問：「在我的技術堆疊或環境中，如何實作某條具體要求？」這類問題應由 Cheat Sheet Series 專案覆蓋。驗證方可能會問：「在這個環境中，如何測試這條要求？」這類問題應由 Web Security Testing Guide 專案覆蓋。

ASVS 並非只面向安全專家，但讀者仍需具備理解相關內容所需的技術知識，或能夠自行查閱和理解相關概念。

### 要求

ASVS 特意使用「要求」一詞，因為其中規定的內容是符合本標準所必須達到的。ASVS 正文只收錄必須滿足的要求，不把「應該做到」的建議作為合規條件。

如果某項內容只是眾多可選方案之一，或僅涉及程式碼風格，就不屬於這裡所說的「要求」。

每條 ASVS 要求都針對具體的安全原則，並盡量避免限定某種技術或實作方式；同時，要求本身也應體現設定該要求的原因。因此，ASVS 不會圍繞某一種驗證方法或實作方案來編寫要求。

### 已記錄的安全決策

在軟體安全中，盡早規劃安全設計和擬採用的機制，有助於在最終產品或功能中獲得更一致、更可靠的實作。

有些安全要求實作起來較為複雜，而且具體做法高度依賴應用自身的需求，例如權限管理、輸入驗證，以及針對不同敏感級別資料採取的保護措施。

因此，ASVS 不會籠統地規定「所有資料都必須加密」，也不會試圖用一條要求覆蓋所有場景。對於這類控制，ASVS 要求應用開發方以文件形式記錄所作的決策和具體組態。驗證方可以先判斷這些決策是否合理，再對照文件檢查實際實作是否符合預期。

這些文件要求用於記錄開發組織在實作特定安全要求時作出的決策。

文件要求一律放在各章第一節，但並非每章都有。每條文件要求都會對應一條實施要求，用於確認文件中記錄的決策已經落實。需要注意的是，檢查文件是否存在和檢查實際實作是否到位，是兩項不同的驗證工作。

設定文件要求主要有兩個原因。首先，許多安全要求都要落實一組具體規則，例如允許上傳哪些檔案類型、必須執行哪些業務控制，以及某個欄位可以包含哪些字元。每個應用採用的規則各不相同，因此 ASVS 無法統一規定這些規則，速查表或更詳細的說明也無法解決這一問題。如果不把這些決策記錄下來，驗證方也就無法判斷實際實作是否正確。

其次，有些要求需要給應用開發方留出選擇空間，以便根據實際情況應對安全問題。例如，早期 ASVS 版本對工作階段逾時作出了非常具體的規定，但許多應用，尤其是面向普通使用者的應用，會採用更寬鬆的逾時設定，並輔以其他緩解措施。因此，文件要求明確允許開發方在這方面靈活處理。

這些決策不應由每位開發人員各自作出和記錄，而應由組織統一制定、傳達給開發人員，並在開發過程中貫徹執行。

在軟體開發中，為新功能提供規格說明和設計方案是常規做法；要求開發人員統一使用共用元件和介面機制也很常見。同樣的做法自然也適用於安全領域。

記錄和落實安全決策的方式可以靈活選擇。組織既可以把決策寫入文件供開發人員查閱，也可以將其固化在所有開發人員都必須使用的共用程式碼函式庫中。兩種方式都可以達到預期目的。

## 應用程式安全驗證等級

ASVS 定義了三個安全驗證等級，每個等級的深度和複雜度逐級增加。總體目標是讓組織先從第 1 級開始，處理最關鍵的安全問題，再根據組織和應用需要逐步提升到更高等級。文件和要求文字中可能使用 L1、L2、L3 表示這些等級。

每個 ASVS 等級都規定了達到該等級必須滿足的安全要求。尚未達到的更高等級要求，可以作為後續改進建議。

為了避免重複要求，或避免某些要求在更高等級中不再適用，一些要求會適用於某個特定等級，但在更高等級中附加更嚴格的條件。

### 等級評估

各等級根據要求的優先級劃分，優先級則結合安全要求的實施和測試經驗確定。評估時主要權衡風險降低效果與實作成本，同時盡量降低採用門檻。

評估風險降低效果時，既要考慮要求對機密性、完整性和可用性的保護作用，也要判斷它屬於主要防線還是縱深防禦措施。

專案組對評估標準和等級劃分進行了充分討論，最終方案適用於絕大多數場景，但不可能與所有情況完全吻合。因此，組織可以根據自身面臨的具體風險，提前實施某些更高等級的要求。

各等級中的要求類型大致可以這樣理解。

### 第 1 級

該等級包含保護應用時最少需要考慮的要求，是一個關鍵起點。它大約包含 ASVS 要求的 20%。該等級的目標是盡可能減少要求數量，以降低採用門檻。

這些要求通常是關鍵或基礎的第一層防護要求，用於防止常見攻擊；這些攻擊不需要依賴其他弱點或前置條件就可能被利用。

除第一層防護要求外，一些在更高等級影響較小的要求也放在這裡，例如與密碼相關的要求。這些要求對第 1 級更重要，因為更高等級還涉及多因素身分驗證要求。

第 1 級並不一定能由沒有內部文件或程式碼存取權限的外部測試人員通過滲透測試驗證（例如「黑箱」測試），不過較少的要求數量應能讓驗證更容易。

### 第 2 級

大多數應用都應努力達到這一安全等級。ASVS 中約 50% 的要求屬於 L2，這意味著應用若要符合 L2，需要實作 ASVS 中約 70% 的要求（所有 L1 和 L2 要求）。

這些要求通常涉及不太常見的攻擊，或針對常見攻擊的更複雜防護。它們可能仍然屬於第一層防護，也可能要求攻擊滿足某些前置條件才會成功。

### 第 3 級

希望證明自身達到最高安全水準的應用應以此等級為目標。L3 約佔全部要求的 30%；與 L1、L2 合併後，構成完整的 ASVS 要求集。

本等級中的要求通常是縱深防禦機制，或其他有價值但較難實作的控制。

### 應達到哪個等級

基於優先級的等級旨在反映組織和應用的應用程式安全成熟度。ASVS 不會規定某個應用必須處於哪個等級；組織應分析自身風險，並根據應用敏感性以及應用使用者的期望，決定自己認為應該達到的等級。

例如，只收集有限敏感資料的早期創業公司，可能會把第 1 級作為初始安全目標；但銀行如果想讓客戶相信其網上銀行應用程式安全可靠，可能很難證明低於第 3 級是合理的。

## 如何使用 ASVS

### ASVS 的結構

ASVS 總共包含約 350 條要求，分為 17 個章節，每個章節又進一步劃分為多個小節。

章節和小節劃分的目的，是便於根據應用相關性選擇或過濾章節與小節。例如，對於機器到機器的 API，V3 章中與 Web 前端相關的要求並不適用。如果沒有使用 OAuth 或 WebRTC，那麼這些章節也可以忽略。

### 發佈策略

ASVS 版本號採用「主版本.次版本.補丁版本」的格式，數字變化反映版本的變更範圍：主版本更新第一個數字，次版本更新第二個數字，補丁版本更新第三個數字。

* 主版本發佈 - 全面重組，幾乎所有內容都可能變化，包括要求編號。需要重新評估合規性（例如 4.0.3 -> 5.0.0）。
* 次版本發佈 - 可能新增或刪除要求，但整體編號保持不變。需要重新評估合規性，但通常會更容易（例如 5.0.0 -> 5.1.0）。
* 補丁版本發佈 - 可能刪除要求（例如重複或過時的要求），或降低要求嚴格程度；但符合上一版本的應用也會符合該補丁版本（例如 5.0.0 -> 5.0.1）。

以上說明專門針對 ASVS 中的要求。周邊文字以及附錄等其他內容的變更，不視為破壞性變更。

### 靈活使用 ASVS

前文提到的若干機制，例如文件要求和等級機制，使組織能夠以更靈活、更貼合自身情況的方式使用 ASVS。

此外，強烈鼓勵組織針對自身或所在領域建立專屬分支，依據其應用程式的特性和風險等級調整要求。不過，必須維持可追溯性，確保要求 4.1.1 在所有版本中通過驗證時都具有相同意義。

理想情況下，每個組織都應建立自己的客製化 ASVS，省略無關章節（例如未使用 GraphQL、WebSockets、SOAP 時）。組織專屬的 ASVS 版本或補充文件也適合提供組織內部的實作指引，詳細說明符合各項要求時應使用的程式庫或資源。

### 如何引用 ASVS 要求

每條要求都有一個 `<chapter>.<section>.<requirement>` 格式的識別碼，其中每個元素都是數字。例如：`1.11.3`。

* `<chapter>` 值對應要求所在章節；例如，所有 `1.#.#` 要求都來自「編碼和淨化」章節。
* `<section>` 值對應該章節內要求所在的小節；例如，所有 `1.2.#` 要求都位於「編碼和淨化」章節中的「注入預防」小節。
* `<requirement>` 值識別該章節和小節中的具體要求；例如，`1.2.5` 在本標準 5.0.0 版中是：

> 驗證應用能夠防範作業系統命令注入，且作業系統呼叫採用參數化作業系統查詢，或採用適合命令行情境的輸出編碼。

由於識別碼可能在標準版本之間變化，因此其他文件、報告或工具最好使用以下格式：`v<version>-<chapter>.<section>.<requirement>`，其中 `version` 是 ASVS 版本標籤。例如：`v5.0.0-1.2.5` 應理解為特指 5.0.0 版中「編碼和淨化」章節「注入預防」小節的第 5 條要求。（也可以概括為 `v<version>-<requirement_identifier>`。）

注意：格式中版本號前面的 `v` 應始終使用小寫。

如果識別碼中沒有 `v<version>`，則預設指向最新版 ASVS。由於要求會隨版本演進而變化，這種寫法可能產生歧義，因此編寫文件或開發工具時應始終包含版本號。

ASVS 要求清單會以 CSV、JSON 和其他格式提供，便於引用或在程序中使用。

### ASVS 分支

組織可以通過選擇三個等級之一來採用 ASVS，也可以建立領域專屬分支，根據應用風險等級調整要求。只要能夠保持可追溯性，確保要求 4.1.1 在所有版本中通過驗證時都表示同一件事，就鼓勵採用這種分支方式。

理想情況下，每個組織都應建立自己的客製版 ASVS，省略無關章節（例如未使用 GraphQL、Websockets、SOAP 時，可省略這些內容）。分支應以 ASVS 第 1 級作為基線，再根據應用風險推進到第 2 級或第 3 級。

## ASVS 的使用場景

ASVS 可用於評估應用程式安全性，下一章會對此進行更深入說明。不過，ASVS（或其分支版本）還有其他若干潛在用途。

### 作為詳細的安全架構指南

應用程式安全驗證標準最常見的用途之一，是作為安全架構師的參考資源。關於如何建置安全的應用架構，尤其是現代應用架構，可用資源並不多。ASVS 可以幫助填補這些空白，讓安全架構師能夠為常見問題選擇更好的控制措施，例如資料保護模式和輸入驗證策略。架構和文件要求在這方面尤其有用。

### 作為專門的安全編碼參考

ASVS 可作為應用開發期間準備安全編碼參考的基礎，幫助開發人員在建置軟體時始終考慮安全。雖然 ASVS 可以作為基礎，但組織應準備自己的具體指南，確保其清晰、統一，並且最好基於安全工程師或安全架構師的指導來制定。在此基礎上，也鼓勵組織盡可能準備經批准的安全機制和函式庫，使其既可在指南中引用，也可供開發人員使用。

### 作為自動化單元測試和整合測試指南

ASVS 的設計目標之一是高度可測試。有些驗證是技術性的，而其他要求（例如架構和文件要求）可能需要進行文件或架構審查。圍繞可通過技術手段驗證的要求，建置針對具體且相關濫用場景的單元測試、整合測試和模糊測試，可以更容易地在每次建置時確認這些控制是否正常工作。例如，可以為登入控制器的測試套件編寫額外測試，檢查使用者名稱參數是否存在常見預設使用者名稱、帳號枚舉、暴力破解、LDAP 和 SQL 注入以及 XSS 等問題。同樣，針對密碼參數的測試也應包括常見密碼、密碼長度、空位元組注入、移除參數、XSS 等情況。

### 用於安全開發培訓

ASVS 也可用於定義安全軟體的特徵。許多「安全編碼」課程其實只是倫理駭客課程，再附帶少量編碼建議。這未必能幫助開發人員寫出更安全的程式碼。相反，安全開發課程可以使用 ASVS，並重點講解 ASVS 中的正向機制，而不是只關注 Top 10 中那些「不該做」的負面事項。ASVS 的結構也為講解保護應用時的不同主題提供了清晰順序。

### 作為安全軟體採購指導框架

ASVS 是幫助安全軟體採購或客製開發服務採購的優秀框架。採購方可以直接提出要求：希望採購的軟體必須按 ASVS X 級開發，並要求供應方證明該軟體滿足 ASVS X 級。

## 在實踐中應用 ASVS

不同威脅有不同動機。一些產業擁有獨特的資訊和技術資產，也有特定領域的監管合規要求。

強烈鼓勵組織根據自身業務性質深入審視獨特的風險特徵，並基於這些風險和業務要求確定合適的 ASVS 等級。
