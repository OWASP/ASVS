# 評估與認證

## OWASP 對 ASVS 認證和信任標誌的立場

OWASP 是一家堅持廠商中立原則的非營利組織，不會為任何廠商、驗證方或軟體提供認證。任何聲稱符合 ASVS 的保證、信任標誌或認證，都不代表獲得了 OWASP 官方認可。因此，組織應謹慎看待第三方提出的 ASVS 認證聲明。

組織可以提供保證服務，但不得聲稱獲得 OWASP 官方認證。

## 如何驗證 ASVS 合規性

ASVS 不會像測試指南那樣詳細規定合規驗證方法，但仍有幾個關鍵問題需要說明。

### 驗證報告

傳統滲透測試報告通常只列出未通過的項目。ASVS 認證報告則應說明驗證範圍，匯總所有已檢查的要求，列明未通過的要求，並給出問題處理建議。對於不適用的要求（例如無狀態 API 中的工作階段管理要求），也必須在報告中明確標注。

### 驗證範圍

開發應用的組織通常不會實施全部要求，因為根據應用的功能，某些要求可能不相關，或重要性較低。驗證方應明確說明驗證範圍，包括組織希望達到的等級以及本次實際納入的要求。報告應以納入驗證的內容為主，而不能只羅列排除項。對於未實作且被排除的要求，驗證方還應評價排除理由是否合理。

只有這樣，報告使用者才能瞭解驗證背景，並據此判斷該應用在多大程度上值得信任。

認證組織可以自行選擇測試方法，但應在報告中披露這些方法，並且理想情況下應可重複執行。根據應用和要求的不同，可以採用人工滲透測試、原始程式碼分析等不同方法來驗證輸入驗證等方面。

### 驗證機制

驗證具體的 ASVS 要求往往需要綜合運用多種方法。除了使用有效身分驗證資訊開展滲透測試，以覆蓋應用的全部功能外，驗證方可能還需要查閱文件、原始程式碼和組態，並與開發流程的參與者溝通。驗證 L2 和 L3 要求時尤其如此。通常的做法是提供有力證據和詳細記錄來支援驗證發現，這些材料可包括工作底稿、截圖、腳本和測試日誌。僅執行自動化工具而不開展深入測試，不足以支援認證結論，因為每條要求都必須得到切實驗證。

使用自動化來驗證 ASVS 要求一直是大家關注的話題。因此，有必要澄清一些與自動化測試和黑盒測試相關的要點。

#### 自動化安全測試工具的作用

將動態和靜態應用程式安全測試工具（DAST 和 SAST）正確整合到建置流水線後，可以發現一些本不應出現的安全問題。但如果沒有經過妥善組態和調優，這些工具往往無法達到所需的覆蓋範圍；過多的誤報和無關結果還會妨礙真正安全問題的發現和處理。

這類工具或許能夠覆蓋一些較基礎、較直接的技術要求，例如與輸出編碼或淨化有關的要求。但必須注意，這些工具無法完整驗證許多較複雜的 ASVS 要求，或與業務邏輯和存取控制有關的要求。

較複雜的要求也可能實作自動驗證，但需要針對具體應用編寫測試。這些測試與組織現有的單元測試和整合測試類似，因此可以利用現有自動化測試基礎設施來編寫 ASVS 專項測試。這樣做雖然需要前期投入，卻能持續檢查相關要求，長期收益十分明顯。

總之，可自動化測試並不等同於執行現成工具。

#### 滲透測試的作用

4.0 版曾針對「黑盒」測試（無法查看文件和原始程式碼的測試）優化 L1，但即使在當時，標準也明確指出這種方式無法提供有效保證，應積極勸阻採用這種方式。

在無法獲取必要補充資訊的情況下開展測試，是一種低效且無效的安全驗證方式。他們既無法審查原始程式碼，也難以識別潛在威脅和缺失的控制措施，還會失去在較短時間內開展深入測試的機會。

強烈建議開展以文件或原始程式碼為基礎的（混合）滲透測試，使測試人員能夠與應用開發人員充分溝通，並完整查閱應用文件，而不是採用傳統滲透測試方式。要驗證許多 ASVS 要求，這是必要的。
