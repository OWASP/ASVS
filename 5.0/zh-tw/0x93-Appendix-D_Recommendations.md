# 附錄 D：建議

## 引言

在編制應用程式安全驗證標準（ASVS）5.0 版時，我們發現一些既有條目和新增建議不應作為 5.0 的要求納入。這可能是因為按照 5.0 的定義，它們不屬於 ASVS 的範圍；也可能是因為它們雖然值得採納，卻不適合作為強制要求。

為保留其中仍有參考價值的內容，本附錄收錄了部分條目。

## 建議採用、且屬於範圍內的機制

以下條目屬於 ASVS 的討論範圍。雖然不適合作為強制要求，但在建置安全應用時仍強烈建議予以考慮：

* 應提供密碼強度計，幫助使用者設定更強密碼。
* 在應用根目錄或 .well-known 目錄中建立公開可存取的 security.txt 文件，清楚定義供他人聯繫所有者報告安全問題的鏈接或電子郵件位址。
* 除可信服務層驗證外，還應執行用戶端輸入驗證，因為這有助於發現是否有人為攻擊應用而繞過用戶端控制。
* 使用 robots.txt 文件、X-Robots-Tag 回應頭或 robots HTML meta 標籤，防止意外可存取的敏感頁面出現在搜索引擎中。
* 使用 GraphQL 時，在業務邏輯層實作授權邏輯，而不是在 GraphQL 或 resolver 層實作，以避免必須在每個獨立介面上處理授權。

## 軟體安全原則

以下條目曾收錄在 ASVS 中，但嚴格來說並不屬於「要求」。它們是實施安全控制時可考慮的原則，遵循這些原則有助於提高控制措施的穩健性：

* 安全控制應集中、簡單（設計經濟性）、可驗證其安全性，並且可復用。這應避免重複、缺失或無效控制。
* 盡可能使用已有且經過充分審查的安全控制實作，而不是依賴從零開始實作控制。
* 理想情況下，應使用單一存取控制機制存取受保護資料和資源。所有請求都應經過這一單一機制，以避免複製貼上或不安全替代路徑。
* 基於屬性或功能的存取控制是一種推薦模式，即程式碼檢查使用者是否被授權存取某個功能或資料項，而不是只檢查其角色。權限仍應通過角色分配。

## 軟體安全流程

ASVS 5.0 刪除了若干與安全流程有關的條目，但這些流程仍是值得採用的良好實踐。有關如何有效落實這些流程，可以參考 OWASP SAMM 專案。此前收錄在 ASVS 中的條目包括：

* 驗證使用安全軟體開發生命週期，在開發所有階段處理安全問題。
* 驗證在每次設計變更或迭代規劃時使用威脅建模，以識別威脅、規劃對策、促進適當的風險回應，並指導安全測試。
* 驗證所有使用者故事和功能都包含功能性安全約束，例如「作為使用者，我應能夠查看和編輯我的個人資料。我不應能夠查看或編輯其他任何人的個人資料」。
* 驗證所有開發人員和測試人員都可以存取安全編碼檢查清單、安全要求、指南或策略。
* 驗證存在持續執行的流程，確保應用原始程式碼不含後門、惡意程式碼（例如「切香腸」攻擊、邏輯炸彈、時間炸彈），以及未記錄或隱藏的功能（例如彩蛋、不安全的調試工具）。如果無法完整存取包括第三方庫在內的所有原始程式碼，就無法滿足本條，因此它可能只適用於要求最高安全級別的應用。
* 驗證已部署環境具備用於檢測和回應組態漂移的機制。這可以包括使用不可變基礎設施、根據安全基線自動重新部署，或使用漂移檢測工具將當前狀態與獲批准的組態進行比較。
* 驗證所有第三方產品、庫、框架和服務都按其各自建議進行了組態加固。
