# V12 安全通訊

## 控制目標

本章規定如何保護傳輸中的資料，既包括終端使用者用戶端與後端服務之間的通訊，也包括應用內部各服務之間的通訊。

本章主要強調以下安全原則和最佳實務：

* 確保對外通訊已加密，理想情況下內部通訊也應加密。
* 按照現行安全建議組態通訊加密機制，包括選用當前推薦的演算法和密碼套件。
* 通過使用經簽章的憑證，確保通訊不被未授權方攔截。

除上述安全原則和最佳實務外，附錄 C「密碼學標準」還提供了有關密碼機制安全強度的詳細技術說明。

## V12.1 通用 TLS 安全指導

本節給出保護 TLS 通訊的基本要求。應用應持續使用最新工具檢查 TLS 組態。

萬用字元 TLS 憑證本身並非不安全。但如果同一張憑證部署在所有自有環境中（例如正式、預備、開發和測試環境），該憑證遭到攻破可能危及使用它的應用的安全。因此，應盡可能妥善保護和管理憑證，並在不同環境中使用獨立的 TLS 憑證。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **12.1.1** | 驗證應用只啟用當前仍受推薦的 TLS 版本，例如 TLS 1.2 和 TLS 1.3，並優先使用其中最新的版本。 | 1 |
| **12.1.2** | 驗證應用只啟用當前推薦的密碼套件，並優先選擇其中安全強度最高的套件。L3 應用只能支援具備前向保密性的密碼套件。 | 2 |
| **12.1.3** | 驗證應用在根據 mTLS 用戶端憑證的身分進行身分驗證或授權之前，先確認該憑證可信。 | 2 |
| **12.1.4** | 驗證應用啟用並組態了適當的憑證吊銷機制，例如線上憑證狀態協議（OCSP）的回應附帶機制（OCSP Stapling）。 | 3 |
| **12.1.5** | 驗證應用的 TLS 組態啟用了加密 ClientHello（ECH），以防止伺服器名稱指示（SNI）等敏感中繼資料在 TLS 握手過程中暴露。 | 3 |

## V12.2 與面向外部的服務進行 HTTPS 通訊

應用所有對外提供的 HTTP 服務都必須使用加密連線，並採用公開受信任的憑證。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **12.2.1** | 驗證用戶端與所有對外 HTTP 服務之間的連線都使用 TLS，並且不會降級為不安全或未加密的通訊。 | 1 |
| **12.2.2** | 驗證面向外部的服務使用公開受信任的 TLS 憑證。 | 1 |

## V12.3 通用服務間通訊安全

伺服器對內和對外的通訊並不只有 HTTP。應用與其他系統之間的所有入站和出站連線也必須受到保護，並應盡可能使用 TLS。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **12.3.1** | 驗證所有進出應用的連線都使用 TLS 等加密協議，包括與監控系統、管理工具、遠端存取和 SSH 服務、中介軟體、資料庫、大型機、合作夥伴系統及外部 API 的連線。服務不得降級為不安全或未加密的協議。 | 2 |
| **12.3.2** | 驗證 TLS 用戶端在與伺服器交換資料之前，會檢查伺服器提供的憑證是否可信且有效。 | 2 |
| **12.3.3** | 驗證應用內部基於 HTTP 的服務之間全部使用 TLS 或其他合適的傳輸加密機制，而且不會降級為不安全或未加密的通訊。 | 2 |
| **12.3.4** | 驗證內部服務之間的 TLS 連線使用可信憑證。如果憑證由內部 CA 簽發，發起連線的服務必須只信任明確指定的內部 CA；如果使用自我簽署憑證，則必須只信任明確指定的自我簽署憑證。 | 2 |
| **12.3.5** | 驗證系統內部相互通訊的服務採用強身分驗證方式，以確認每個端點的身分。這裡的強身分驗證必須基於公開金鑰基礎設施，並能抵抗重放攻擊，例如 TLS 用戶端身分驗證。微服務架構可以使用服務網格來簡化憑證管理並加強安全控制。 | 3 |
