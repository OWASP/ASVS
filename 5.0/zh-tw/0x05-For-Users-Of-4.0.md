# 與 v4.x 相比的變化

## 引言

熟悉本標準 4.x 版本的使用者，可能會發現回顧 5.0 版引入的關鍵變化很有幫助。這些變化包括內容、範圍和底層理念的更新。

在 4.0.3 版的 286 條要求中，只有 11 條保持不變，另有 15 條僅做了不改變含義的輕微語法調整。總計有 109 條要求（38%）在 5.0 版中不再作為獨立要求存在，其中 50 條直接刪除，28 條因重複被移除，31 條被合併到其他要求。其餘要求都以某種方式進行了修訂。即便內容沒有實質性變化的要求，也會因為重新排序或結構調整而擁有不同識別碼。

為了便於使用者遷移到 5.0 版，標準提供了映射文件，用於追蹤 4.x 與 5.0 要求之間的對應關係。映射文件獨立於正式版本發佈，必要時可以單獨更新或補充說明。

## 要求理念

### 範圍和重點

4.x 版本包含了一些不符合標準預期範圍的要求，這些要求已經被移除。不符合 5.0 範圍標準或不可驗證的要求也已被排除。

### 更強調安全目標，而不是具體機制

在 4.x 版本中，許多要求關注具體機制，而不是底層安全目標。在 5.0 版中，要求圍繞安全目標展開，只有當某種機制是唯一可行方案時才會引用具體機制，或把具體機製作為示例或補充說明。

同一安全目標往往可以通過多種方式實作。採用這種寫法，可以避免因不必要地限定實作方式而影響組織的靈活選擇。

此外，針對同一安全關注點的要求，也已在適當情況下進行了合併。

### 已記錄的安全決策

「已記錄的安全決策」看似是 5.0 版新增的概念，其實源自 4.0 版中有關策略執行和威脅建模的要求。早期版本的一些要求已經隱含要求組織先開展分析，再據此實施安全控制，例如確定允許建立哪些網路連接。

5.0 版將這些內容明確寫成文件要求，確保實施和驗證時能夠取得所需資訊，也使要求更加清晰、可執行、可驗證。

## 結構變化和新增章節

5.0 版中有幾個章節引入了全新內容：

* OAuth 和 OIDC - 鑒於這些協議在存取委派和單一登入中的廣泛採用，標準新增了專門要求，以覆蓋開發人員可能遇到的多種場景。該領域未來可能會發展成獨立標準，類似早期版本中對移動和 IoT 要求的處理。
* WebRTC - 隨著這一技術越來越流行，其獨特的安全考慮和挑戰現在由專門章節覆蓋。

標準還重新整理了章節和小節，使相關要求能夠集中歸類。

這種重組帶來了若干新增章節：

* 自包含權杖 - 自包含權杖過去歸入工作階段管理，現在被視為一種獨立機制，也是無狀態通信（例如 OAuth 和 OIDC）中的基礎元素。由於它們具有獨特安全影響，標準用專門章節處理，並在 5.x 版中引入了一些新要求。
* Web 前端安全 - 隨著基於瀏覽器的應用越來越複雜，以及僅 API 架構興起，前端安全要求被拆分為獨立章節。
* 安全編碼和架構 - 一些無法歸入現有章節的通用安全實踐新要求，被集中放在這裡。

5.0 版中的其他組織結構調整，主要是為了澄清意圖。例如，輸入驗證要求被移到業務邏輯旁邊，體現其在執產業務規則中的作用，而不是繼續與淨化和編碼放在一起。

原 V1 架構章節已被移除。它最初的小節包含超出範圍的要求，後續小節則已重新分配到相關章節，並在必要時去重和澄清。

## 移除與其他標準的直接映射

標準正文不再直接列出與其他標準的映射。專案計畫改為將 ASVS 映射到 OWASP Common Requirement Enumeration（CRE），再由 CRE 建立 ASVS 與其他 OWASP 專案及外部標準之間的聯繫。

與 CWE 和 NIST 的直接映射不再維護，原因如下。

### 降低與 NIST 數位身分指南的耦合

NIST [數位身分指南（SP 800-63）](https://pages.nist.gov/800-63-3/) 長期以來一直是身分驗證和授權控制的參考。4.x 版本中，某些章節與 NIST 的結構和術語高度一致。

雖然這些指南仍是重要參考，但嚴格對齊也帶來了挑戰，包括使用的術語不夠廣為人知、類似要求重複，以及映射不完整。5.0 版不再採用這種方式，以提升清晰度和相關性。

### 不再直接映射通用弱點枚舉（Common Weakness Enumeration，CWE）

[通用弱點枚舉（Common Weakness Enumeration，CWE）](https://cwe.mitre.org/) 為軟體安全弱點提供了一套實用的分類體系。不過，有些 CWE 條目僅表示類別，一條要求也難以準確映射到單個 CWE；此外，4.x 版本還存在部分映射不準確的問題。因此，5.0 版不再維護與 CWE 的直接映射。

## 重新思考等級定義

4.x 版本將等級描述為 L1（「最低」，Minimum）、L2（「標準」，Standard）和 L3（「高級」，Advanced），並暗示所有處理敏感資料的應用至少應滿足 L2。

5.0 版解決了這種做法中的若干問題，下文會逐一說明。

從實際角度看，4.x 版本使用勾選標記作為等級指示，而 5.x 在標準的所有格式中都使用簡單數字，包括 Markdown、PDF、DOCX、CSV、JSON 和 XML。為保持向後相容，仍會生成使用勾選標記的舊版 CSV、JSON 和 XML 輸出。

### 更容易入門的等級

反饋顯示，第 1 級要求數量過多（約 120 條），再加上它被稱為對多數應用來說「不夠好」的「最低」等級，阻礙了採用。5.0 版希望降低這一門檻，將第 1 級主要定義為第一層防護要求，使該等級的要求更清晰、數量更少。用數字說明：v4.0.3 中共有 278 條要求，其中 128 條為 L1，佔 46%；5.0.0 中共有 345 條要求，其中 70 條為 L1，佔 20%。

### 可測試性謬誤

在 4.x 版本中，選擇第 1 級控制時，一個關鍵因素是它們是否適合通過「黑盒」外部滲透測試評估。然而，這種方式並未完全符合第 1 級作為最低安全控制集合的意圖。一些使用者認為第 1 級不足以保護應用，另一些使用者則發現它太難測試。

以可測試性作為等級劃分標準具有相對性，有時也會產生誤導。某條要求可以驗證，並不意味著能夠輕鬆或自動完成驗證。此外，最容易測試的要求，未必最能提高安全性，也未必最容易實作。

因此，在 5.0 版中，等級決策主要基於風險降低，同時也考慮實作成本。

### 不只是風險

基於風險並規定某些應用必須達到特定等級的做法，已經被證明過於僵化。實踐中，安全控制的優先級和實作取決於多個因素，包括風險降低效果和實作所需成本。

因此，鼓勵組織根據自身成熟度以及希望向使用者傳達的資訊，達到其認為自身應該達到的等級。
