# V11 密碼學

## 控制目標

本章介紹應用密碼技術時普遍適用的最佳實務，幫助讀者理解基本原則，並推動應用採用更現代、更能適應未來變化的方案。主要目標包括：

* 建立安全可靠的密碼技術體系，確保系統能夠安全處理故障、應對不斷變化的威脅，並為未來的技術遷移做好準備。
* 採用安全且符合產業最佳實務的密碼機制。
* 建立安全的金鑰管理體系，並實施適當的存取控制和稽核。
* 定期評估密碼技術的發展和應用情況，識別新的風險，並相應調整所用演算法。
* 在應用的整個生命週期內識別和管理密碼技術的應用場景，確保所有相關資產均已登記並得到妥善保護。

除了一般原則和最佳實務，附錄 C「密碼學標準」還提供了更深入的技術說明，並列出了本章認可使用的演算法和工作模式。

秘密管理、通信安全等具體場景所涉及的密碼技術要求，分別列在本標準的其他章節。

## V11.1 密碼資產清單和文件

應用需要建立安全可靠的密碼技術架構，根據資料分類採取相應的保護措施。所有內容一律加密會浪費資源；完全不加密又可能違反法律義務。二者之間的取捨應在架構設計、高層設計、設計衝刺或架構探索階段完成。等到開發後期再臨時拼湊或補救密碼技術方案，成本通常遠高於從一開始就做好設計。

確保定期識別、清點和評估所有密碼資產至關重要。具體方法請參見附錄。

密碼技術體系還需要能夠應對未來量子運算發展帶來的安全風險。後量子密碼學（PQC）指為抵御量子電腦攻擊而設計的密碼演算法；量子電腦預計能夠破解 RSA 和橢圓曲線密碼學（ECC）等廣泛使用的演算法。

關於經過審查的 PQC 原語和標準的當前指導，請參見附錄。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **11.1.1** | 驗證應用制定了書面的金鑰管理策略，並按照 NIST SP 800-57 等標準管理金鑰的整個生命週期。策略應防止金鑰被過度共享；例如，共享秘密最多只供兩個實體使用，私密金鑰只能由一個實體持有。 | 2 |
| **11.1.2** | 驗證應用建立並持續更新密碼資產清單，對應用使用的所有金鑰、演算法和憑證進行登記。對於每個金鑰，清單還必須說明其可以和不可以在系統的哪些位置使用，以及可以和不可以保護哪些類型的資料。 | 2 |
| **11.1.3** | 驗證應用使用相應的工具或機制，識別系統中的所有密碼運算，包括加密、雜湊和數位簽章。 | 3 |
| **11.1.4** | 驗證應用持續維護密碼資產清單，並在其中記錄遷移到新密碼技術標準（例如後量子密碼學）的計畫和路徑，以應對未來威脅。 | 3 |

## V11.2 密碼技術的安全實作

本節規定如何選擇、實作和持續管理應用的核心密碼演算法，目標是確保只部署安全可靠、得到業界認可的密碼學原語，並符合現行標準（例如 NIST、ISO/IEC）和最佳實務。組織必須確保每個密碼元件的選擇都以經過同行評審的證據和實際安全測試為依據。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **11.2.1** | 驗證所有密碼運算都採用經過業界檢驗的實作，包括函式庫和硬體加速實作。 | 2 |
| **11.2.2** | 驗證應用在設計上具備密碼敏捷性，可以隨時重新組態、升級或替換亂數生成演算法、具驗證性的加密演算法、MAC 或雜湊演算法、金鑰長度、迭代輪數、密碼演算法和工作模式，以應對密碼機制被攻破的風險。同樣，應用還必須能夠更換金鑰和密碼，並重新加密資料。這樣，當獲認可的後量子密碼方案或標準的高保證實作廣泛可用時，應用就能平穩升級到後量子密碼學（PQC）。 | 2 |
| **11.2.3** | 驗證所有密碼學原語在所用演算法、金鑰長度和組態下，至少達到 128 位元安全強度。例如，256 位元 ECC 金鑰約等於 128 位元安全強度；RSA 則需要 3072 位元金鑰才能達到同等水準。 | 2 |
| **11.2.4** | 驗證所有密碼運算均採用常數時間實作，比較、計算和傳回過程中不會因「短路」而提前結束，從而避免通過執行時間洩露資訊。 | 3 |
| **11.2.5** | 驗證所有密碼模組在發生故障時都能保持安全，且錯誤處理方式不會導致填補預言機攻擊等弱點。 | 3 |

## V11.3 加密演算法

採用基於 AES 或 ChaCha20 的具驗證性的加密演算法，是現代密碼技術實踐的基礎。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **11.3.1** | 驗證應用沒有使用 ECB 等不安全的區塊密碼工作模式，也沒有使用 PKCS#1 v1.5 等強度不足的填充方案。 | 1 |
| **11.3.2** | 驗證應用只使用本標準認可的加密演算法和工作模式，例如 AES-GCM。 | 1 |
| **11.3.3** | 驗證加密資料同時受到完整性保護，攻擊者無法在未獲授權的情況下修改資料。應優先採用本標準認可的具驗證性的加密演算法；也可以把本標準認可的加密演算法與本標準認可的 MAC 演算法組合使用。 | 2 |
| **11.3.4** | 驗證同一個 nonce、初始化向量或其他一次性數值不會在不同的「加密金鑰與資料」組合中重複使用。生成這些數值的方法必須符合所用演算法的要求。 | 3 |
| **11.3.5** | 驗證加密演算法與 MAC 演算法組合使用時，始終採用「先加密、後計算 MAC」（Encrypt-then-MAC）的順序。 | 3 |

## V11.4 雜湊和基於雜湊的函數

安全雜湊函數用於數位簽章、HMAC、金鑰衍生函數（KDF）、隨機位元產生和密碼儲存等多種密碼協議。整個密碼技術體系的安全性取決於底層雜湊函數的強度。本節說明密碼運算使用安全雜湊函數時需要滿足的要求。

關於密碼儲存和附錄中的相關內容，還可以參考 [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#password-hashing-algorithms)。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **11.4.1** | 驗證數位簽章、HMAC、KDF、隨機位元產生等需要密碼學安全性的用途只採用本標準認可的雜湊函數。MD5 等被禁止的雜湊函數不得用於任何需要密碼學安全性的場景。 | 1 |
| **11.4.2** | 驗證密碼使用本標準認可且計算成本足夠高的金鑰衍生函數（也稱「密碼雜湊函數」）進行儲存，並按照最新指導組態參數。參數需要兼顧安全性和效能，使暴力破解在目標安全等級下足夠困難。 | 2 |
| **11.4.3** | 驗證數位簽章、資料鑑別或完整性保護所使用的雜湊函數具有所需的抗碰撞能力和足夠的輸出長度。需要抗碰撞時，輸出長度至少為 256 位元；只需抵抗第二原像攻擊時，輸出長度至少為 128 位元。 | 2 |
| **11.4.4** | 驗證應用從密碼衍生秘密金鑰時，使用本標準認可的金鑰衍生函數，並設定金鑰拉伸參數。這些參數必須兼顧安全性和效能，防止暴力破解攻擊危及衍生出的密碼學金鑰。 | 2 |

## V11.5 隨機值

密碼學安全偽亂數產生器（CSPRNG）很難自行正確實作。系統中的高品質熵源可能因過度使用而耗盡；隨機性不足的來源又會生成可預測的金鑰和秘密。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **11.5.1** | 驗證所有需要防止猜測的亂數和隨機字串都由密碼學安全偽亂數產生器（CSPRNG）生成，並且至少包含 128 位元熵。UUID 不滿足此要求。 | 2 |
| **11.5.2** | 驗證亂數生成機制即使在請求量很高時也能安全、可靠地工作。 | 3 |

## V11.6 公開金鑰密碼學

公開金鑰密碼技術適用於多個參與方之間無法共享或不宜共享秘密金鑰的場景。

為確保所用密碼機制能夠抵御現代威脅，需要採用本標準認可的金鑰交換機制，例如 Diffie-Hellman 和橢圓曲線 Diffie-Hellman（ECDH）。「安全通信」章節已經規定了 TLS 要求，因此本節適用於在 TLS 之外使用公開金鑰密碼學的場景。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **11.6.1** | 驗證生成金鑰、為金鑰生成過程提供隨機種子，以及生成和驗證數位簽章時，只採用本標準認可的密碼演算法和工作模式。金鑰生成演算法不得產生容易受到已知攻擊的弱金鑰，例如容易被 Fermat 分解法破解的 RSA 金鑰。 | 2 |
| **11.6.2** | 驗證 Diffie-Hellman 等金鑰交換使用本標準認可的密碼演算法和安全參數，防止攻擊者破壞金鑰建立過程，進而實施中間人攻擊或破壞密碼機制的安全性。 | 3 |

## V11.7 使用中資料的密碼保護

保護正在處理中的資料至關重要。建議採用全記憶體加密、傳輸中資料加密等技術，並確保資料在使用後盡快加密。

| # | 描述 | 級別 |
| :---: | :--- | :---: |
| **11.7.1** | 驗證應用採用全記憶體加密，在敏感資料處理期間防止未經授權的使用者或處理程序存取這些資料。 | 3 |
| **11.7.2** | 驗證應用遵循資料最小化原則，把處理過程中暴露的資料降到最低，並在使用完畢後立即或在可行的情況下盡快加密。 | 3 |
